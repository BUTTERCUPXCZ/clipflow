## Key implementation decisions
- **The Python media layer is synchronous.** `FfmpegRunner` uses `subprocess.Popen` with an argument list and no shell. RQ jobs run synchronously in the forked worker, and the async gRPC server calls the same `MediaProber` through `asyncio.to_thread`. One implementation serves both.
- **NestJS is a hybrid app.** It serves HTTP plus a `JobEventsService` gRPC server (`app.connectMicroservice`, Transport.GRPC on `JOB_EVENTS_GRPC_URL`), and a WebSocket gateway on `/ws` (`WsAdapter`) with an Origin check on upgrade.
- **Event application is one guarded SQL update:** `WHERE id = $1 AND last_sequence < $seq AND status NOT IN (terminal)`. Duplicate, out-of-order and late events are dropped by the database, not by in-memory state.
- **Test fixtures are generated by ffmpeg at test time** (`testsrc` + `sine`, 2–3 s), so no binary video files are committed.
- **`npm run dev:ai` starts the gRPC/HTTP service and the RQ worker together** (open question 2). `dev:worker` runs the worker alone.

## Risks
| Risk | Mitigation |
|---|---|
| The RQ fork model and gRPC channels (fork-unsafe) | The worker creates its gRPC channel inside the job, after the fork; nothing grpc-related is created at import time |
| An ffmpeg orphaned on cancel or crash | Its own process group; SIGTERM, then SIGKILL after 5 s; tested by checking the PID is gone |
| WebSocket in the Tauri webview (CSP, origin) | CSP already allows `ws://localhost:3000`; the Origin allowlist covers all three desktop origins; a manual check in T8 |
| Disk use from frames (1/s at 768 px, about 60–100 KB each) | ~600 frames ≈ 50 MB for 10 min; artifacts are removed with their video or project |

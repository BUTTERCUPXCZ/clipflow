# Implementation Plan: Phase 2 — Projects and Video Import

Source spec: `spec/SPEC-phase-2.md` (approved 2026-11-26). Code standard: `CLAUDE.md` (OOP + SOLID, ≤ 300 lines/file).
Task list: `tasks/phase-2-todo.md`. Phase 1 plan/tasks remain in `tasks/plan.md` / `tasks/todo.md`.
Work happens on branch `phase-2`, merged to `main` after review.

## Overview

First real product feature. The user creates projects and imports local video files into them. Each file is
validated, then copied in the background into `MEDIA_ROOT`, with progress the desktop polls. Everything persists in
PostgreSQL through Drizzle, scoped to a single local user. The Python service is untouched.

## Architecture Decisions

- **Layering (API).** Each layer has one job:
  - controller: HTTP only
  - service: use cases
  - repository (one concrete Drizzle class): all SQL
  - `MediaStorage`: every filesystem path and operation under `MEDIA_ROOT`

  Services never import Drizzle or `fs`. Service unit tests inject fake repositories and storage. Repository
  tests run against the real `clipforge_test`.
- **Drizzle over the existing pool.**
  - A `DRIZZLE` provider wraps `PG_POOL` (`drizzle(pool, { schema })`). The `@nestjs/drizzle` 0.0.2
    pre-release is not used.
  - Migrations are generated by `drizzle-kit` and committed. A custom `drizzle-kit generate --custom` migration
    seeds the local user.
  - `MigrationRunner.onModuleInit` applies migrations. Nest awaits it before `listen()`.
- **Auth seam.** `common/current-user.ts` holds `LOCAL_USER_ID` and `@CurrentUser()`. Every repository method takes
  `userId` and filters by it, and anything not found or not owned gives 404. Real auth later replaces only the
  decorator.
- **Validation at the boundary.** A global `StandardSchemaValidationPipe` (Nest 12 built-in) works with zod schemas
  in `*.schemas.ts`. A bad body or a malformed UUID gives 400 before any service code runs.
- **Import, broken into single-purpose classes:**

  | Class | Job |
  |---|---|
  | `ContainerFormat` table (`container-signatures.ts`) | Extensions, MIME type and a `matches(header)` per family. A new format is one new row |
  | `ImportValidator` | The 7 rules → `ValidatedFile`, or throws `ImportRejectedError` (mapped to 400) |
  | `MediaCopier` | `pipeline` stream to `.part`, progress callback throttled to 1/s, `AbortSignal`, rename, size re-check |
  | `ImportRegistry` | `Map<videoId, AbortController>` for the copies in flight |
  | `VideosService` | Orchestrates: validate → insert `IMPORTING` → copy (not awaited) → `READY` or `FAILED`. `onApplicationBootstrap` recovers stale `IMPORTING` rows |

- **`bigint` uses `mode: 'number'`** (50 GiB ≪ 2^53), so JSON stays plain numbers.
- **Desktop.**
  - `ApiClient` gains `getJson`, `sendJson` and `ApiError` (status plus the server message). Feature `api.ts` modules
    depend on the `api` instance, and `queries.ts` hold the TanStack hooks. Components only render.
  - The videos query sets `refetchInterval: anyImporting ? 1000 : false`.
  - `file-picker.ts` is the only place that touches `@tauri-apps/plugin-dialog`, so tests mock one module.
- **Tests.** DB suites use `TEST_DATABASE_URL` (the `clipforge_test` database, which exists). A Vitest `globalSetup`
  migrates it once. Suites truncate in `beforeEach` and run with `fileParallelism: false`.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| drizzle-kit + ESM `nodenext` (`.js` import suffixes in the schema file) | Med | T1 proves `generate` and T2 proves `migrate` + one query before any feature work. The schema file imports only from `drizzle-orm` |
| Multi-GB copy starves the API | Med | Stream `pipeline` only; progress DB writes ≤ 1/s; Checkpoint C checks `/health` stays responsive mid-copy |
| A partial file mistaken for complete | High | `.part` + rename + size re-check; startup recovery; spec criterion 5 tested by killing the API mid-copy |
| Validation bypass (symlink, traversal, source inside `MEDIA_ROOT`) | High | `lstat` + `realpath` against `realpath(MEDIA_ROOT)`; mutation checks at Checkpoint C |
| Flaky DB tests | Med | Separate DB, truncate per test, no file parallelism for DB suites |
| Linux file portal quirks or a missing capability | Low | `cargo check` validates the capability; a manual multi-select pick in T13 |
| Files creeping past 300 lines (`VideosService` is the likeliest) | Low | `npm run check:lines` runs in `npm test`; the import steps already live in their own classes |

# Implementation Plan: Phase 1 — Application Foundation

Source spec: `doc/system-design.md` §17 Phase 1, `doc/architecture.md` §3–5, §8, §13.
Task list: `tasks/todo.md`.

## Overview

Get all three applications running and talking to each other, with no product features yet:
Tauri desktop → NestJS (REST) → Python AI service (gRPC), plus local PostgreSQL, Redis, Ollama, FFmpeg
and `MEDIA_ROOT` health-checked. The end state is a desktop "System Status" screen that shows every
dependency green or red, backed by real checks.

## Phase 1 acceptance criteria (from the spec)

- Desktop application starts.
- NestJS starts.
- Python service starts.
- PostgreSQL connection works (local, decided after planning; was Supabase Cloud).
- Desktop can call NestJS.
- NestJS can communicate with Python.

## Architecture Decisions

- **Monorepo tooling: npm workspaces + uv.** `apps/desktop` and `apps/api` are npm workspaces
  (npm ships with Node; pnpm isn't installed). `apps/ai-service` is a uv project (uv 0.13 is installed).
- **Node 22, pinned in `.nvmrc`.** The system `/usr/bin/node` is v18, which is too old for Vite and Tauri.
- **One proto source at `proto/ai/v1/`.** Both services read the same file, so the contract can't drift.
  This changes the docs, which show a copy under each app; the docs are updated to match.
  - NestJS loads it at runtime with `@grpc/proto-loader`, so it needs no `protoc`.
  - Python generates stubs with `grpcio-tools`, which bundles its own `protoc`. Stubs go in a gitignored folder.
- **Phase 1 gRPC surface is just `VideoAnalysisService.GetModelStatus`.** It's real spec behavior: it checks
  that Ollama is reachable and the configured vision model is installed. That's enough to prove
  NestJS → Python works. The other RPCs arrive in the phases that need them.
- **The Python process runs FastAPI (`:8000`) and the gRPC server (`:50051`) together** on one asyncio loop.
  The RQ worker becomes its own process in Phase 3.
- **NestJS reaches Postgres with `pg`, using `DATABASE_URL`.** The health check runs `SELECT 1`. Picking an ORM
  or migration tool is a Phase 2 decision, because there are no tables yet.
- **One root `.env`** that every app reads, plus a committed `.env.example`. Config is validated at startup:
  zod in NestJS, pydantic-settings in Python. A missing or invalid variable stops startup with a clear error.
- **Structured logs from the start.** `nestjs-pino` in NestJS, `structlog` in Python. Rust `tracing` waits
  until the desktop has native code worth logging.
- **Desktop:** create-tauri-app (React + TS + Vite), Tailwind v4, shadcn/ui, TanStack Router (code-based
  routes in `src/app/router.tsx`), and TanStack Query. NestJS allows CORS only for the Tauri origins.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Local DB role/database not created yet | High: blocks "PostgreSQL connection works" | User runs the two `sudo -u postgres` commands in README. Health reports `database: error` instead of crashing |
| Redis AOF is off (`appendonly no`) | Med: the queue wouldn't survive a restart | Turn it on with `CONFIG SET appendonly yes` + `CONFIG REWRITE` (needs user OK, since it's a system service). Health reports it |
| Shells without nvm use Node 18 | Med: confusing build failures | `.nvmrc` + an `engines` field. Scripts fail fast on the wrong Node |
| Tauri WebKitGTK quirks on Linux | Med | All system libs are already present (webkit2gtk-4.1 2.52). Check the scaffold launches before building UI on it (Task 7 comes before Task 8) |
| gRPC codegen drift between Node and Python | Low | Single proto file. Python stubs are regenerated by a script and never hand-edited |

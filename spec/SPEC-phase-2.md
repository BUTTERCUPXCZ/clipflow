# Spec: Phase 2 — Projects and Video Import — V1

Status: approved (2026-11-26)
Source: `doc/system-design.md` §4.1, §6.1–6.2, §8, §17 Phase 2; `doc/architecture.md` §9, §11.
Builds on: Phase 1 (`tasks/plan.md`, branch `phase-1`).

## Objective

Let a creator organise footage into **projects** and **import** local video files into them, so the files are
ready for AI processing in Phase 3. ClipForge copies each imported file into its own media directory. The
user's original is never touched. Everything the user creates is still there after the app and API restart.

User: one content creator working on their own machine (single local user, no login).

User stories:
1. I create a project, give it a name (and optionally a description), and see it in my project list.
2. I rename a project or delete it. Deleting asks me to confirm and removes its videos too.
3. In a project, I click **Import videos**, pick one or more files in the native file dialog, and each appears
   at once with a progress bar until it is ready.
4. I see each video's name, size, status, and (from Phase 3) its duration and resolution.
5. I delete a video I no longer need, even while it is still importing.
6. If something is wrong with a file (not a video, too big, disk full), I am told why and nothing is half-written.

## Decisions (approved before this spec)

| Decision | Choice | Consequence |
|---|---|---|
| Authentication | **Single local user**, no login | A fixed local user row. Every request runs as that user via a `CurrentUser` seam, so real accounts can slot in later without reshaping data. The API stays bound to 127.0.0.1. |
| DB tooling | **Drizzle** (`drizzle-orm` + `drizzle-kit`) | Schema in TypeScript and typed queries. SQL migrations are generated, committed and run at API startup. Drizzle wraps the existing `pg` pool (`PG_POOL`); the pre-release `@nestjs/drizzle` 0.0.2 is not used. |
| Media metadata | **Phase 3**, via Python FFprobe | Phase 2 stores file facts: name, size, MIME type. `duration`, `width`, `height` and `frame_rate` stay `NULL` and the UI shows "—". NestJS never runs FFmpeg. |
| Import progress | **Polling** | `POST …/import` returns 202 at once with `IMPORTING`. NestJS copies in the background and records `bytes_copied`. The desktop refetches every second while anything is importing. WebSockets arrive with job progress in Phase 3. |

## Data Model

Migrations live in `apps/api/drizzle/`. They are generated by `drizzle-kit generate`, committed, and applied at API startup by `migrate()`.

```text
users
  id            uuid  PK
  display_name  text  NOT NULL
  created_at    timestamptz NOT NULL default now()
  -- the first migration seeds one row: LOCAL_USER_ID = 00000000-0000-4000-8000-000000000001, "Local user"

projects
  id            uuid  PK default gen_random_uuid()
  user_id       uuid  NOT NULL → users(id) ON DELETE CASCADE      (index)
  name          text  NOT NULL   -- trimmed, 1–100 chars
  description   text  NULL       -- ≤ 1000 chars
  created_at, updated_at  timestamptz NOT NULL default now()

source_videos
  id            uuid  PK default gen_random_uuid()
  project_id    uuid  NOT NULL → projects(id) ON DELETE CASCADE   (index)
  user_id       uuid  NOT NULL → users(id) ON DELETE CASCADE
  filename      text  NOT NULL   -- original basename, display only
  storage_path  text  NOT NULL   -- relative to MEDIA_ROOT
  file_size     bigint NOT NULL
  bytes_copied  bigint NOT NULL default 0
  mime_type     text  NOT NULL
  status        text  NOT NULL CHECK (status IN ('IMPORTING','READY','FAILED'))
  error_message text  NULL
  duration double precision NULL, width int NULL, height int NULL, frame_rate double precision NULL  -- Phase 3
  created_at, updated_at  timestamptz NOT NULL default now()
```

Media layout (architecture §9.2): `MEDIA_ROOT/original-videos/{user_id}/{project_id}/{video_id}/source.{ext}`.
NestJS gains `MEDIA_ROOT` in its env schema (it is already in `.env`).

## API (base `/api/v1`, all scoped to the current user)

| Method | Path | Body / result |
|---|---|---|
| POST | `/projects` | `{name, description?}` → 201 project |
| GET | `/projects` | → projects with `videoCount`, newest `updated_at` first |
| GET | `/projects/:id` | → project |
| PATCH | `/projects/:id` | `{name?, description?}` → project |
| DELETE | `/projects/:id` | → 204. Removes its rows (cascade) and `original-videos/{user}/{project}/` |
| POST | `/projects/:id/videos/import` | `{path}` (absolute) → **202** video in `IMPORTING` |
| GET | `/projects/:id/videos` | → videos, newest first |
| GET | `/videos/:id` | → video (polled during import) |
| DELETE | `/videos/:id` | → 204. Aborts a running copy, removes its row and directory |

Errors: a malformed UUID or invalid body gives **400** with the failing field. An unknown id, or one owned by another user, gives **404**, never 403, so it doesn't reveal that the row exists.

### Import validation (trust boundary)

Every check runs **before** anything is written. A file that fails gets a 400 with a message the UI shows as is.

1. `path` is an absolute string of 1–4096 chars.
2. `lstat`: it exists and is a regular file. Directories, devices and **symlinks** are rejected.
3. **Every common video format is accepted.** The extension must be a known video container, and the MIME type is derived from it:
   - ISO-BMFF: `mp4 m4v mov 3gp 3g2`
   - Matroska: `mkv webm`
   - `avi`
   - MPEG transport stream: `ts mts m2ts`
   - MPEG program stream: `mpg mpeg vob`
   - ASF: `wmv asf`
   - `flv`
   - Ogg: `ogv`
   - `mxf`
4. The container signature matches the extension's family:
   - ISO-BMFF: `ftyp` at byte 4, or a leading `moov`, `mdat`, `wide` or `free` atom for old QuickTime
   - Matroska: EBML `1A45DFA3`
   - AVI: `RIFF…AVI `
   - TS: `0x47` sync at 0 and 188
   - M2TS/MTS: `0x47` at 4 and 196
   - PS: `00 00 01 BA`
   - ASF: `30 26 B2 75 8E 66 CF 11`
   - FLV: `FLV`
   - Ogg: `OggS`
   - MXF: `06 0E 2B 34`

   A renamed `.txt` fails. Whether the codec inside can actually be decoded is FFprobe's job in Phase 3.
5. `0 < size ≤ 50 GiB`.
6. The path is **not inside `MEDIA_ROOT`**.
7. `statfs(MEDIA_ROOT)` free space ≥ size + 1 GiB.

### Background copy

- The video row is inserted as `IMPORTING` with its final `storage_path`, and the endpoint returns 202.
- The file is stream-copied (`pipeline`, never buffered in memory) to `source.{ext}.part`. `bytes_copied` is updated at most once a second. On completion the file is renamed to `source.{ext}`, the size is re-checked, and the status becomes `READY`.
- On a copy error the row becomes `FAILED` with `error_message`, and the `.part` file and video directory are removed.
- **Startup recovery:** any `IMPORTING` row left from a crash becomes `FAILED` ("Import interrupted, import the file again") and its directory is removed.
- Deleting an `IMPORTING` video aborts its copy (`AbortController`) before removing files.

## Desktop

- Sidebar: **Projects** (new, the default route; `/` redirects to `/projects`) and **System status**.
- `/projects`: project cards (name, description, video count, last updated), a **New project** dialog with inline validation, and an empty state with a call to action.
- `/projects/$projectId`:
  - a header with the project name and description, plus **Rename** and **Delete** (an AlertDialog confirm, never `window.confirm`)
  - **Import videos** (native dialog, multi-select, video filter) → one `import` call per file
  - a video table: filename, size, status badge, a progress bar with % while `IMPORTING`, the error text when `FAILED`, duration and resolution ("—" until Phase 3), and delete
- While any video is `IMPORTING`, its list refetches every 1 s. Polling stops when none is.
- API errors appear inline or in the dialog. An unreachable API reuses the Phase 1 `ApiUnreachableError` message.
- Accessibility: every control is named, focus moves into and out of dialogs correctly, and progress uses `role="progressbar"` with a value.

## Code Style

Follow `CLAUDE.md` (OOP + SOLID, at most 300 lines per file) and the Phase 1 refactor:
- Nest modules own their logic. Controllers only map HTTP to service calls. Services depend on injected repositories and storage, never on Drizzle or `fs` directly.
- zod schemas sit in `*.schemas.ts`.
- Every repository method takes `userId` and filters by it.

## Testing Strategy

- **API unit (Vitest):** import validation against real temp files (each rejection rule, plus a symlink, a renamed `.txt` and a file inside MEDIA_ROOT); the copy service (success, mid-copy error, abort, startup recovery) on temp dirs.
- **API integration (Vitest + real Postgres):** services and controllers against a `clipforge_test` database, migrated at suite start and truncated between tests. Covers ownership (another user's id gives 404), cascade delete, and a UUID that is malformed but well-formed in shape.
- **Desktop (Vitest + Testing Library):** project list (empty, error, populated); the create dialog's validation; video rows in IMPORTING with %, READY and FAILED; polling stops once all rows are READY. Tauri dialog and window APIs are mocked, as in Phase 1.
- **Mutation spot-check** in review (code-review-and-quality skill): invert key conditions (symlink check, inside-MEDIA_ROOT check, user scoping) and expect red.
- **Manual end-to-end:** import a real ≥1 GB mp4 and confirm sha256(original) = sha256(copy). Kill the API mid-copy, restart, and see FAILED with no files left. Restart everything and see projects and videos still there.

## Boundaries

- **Always:** validate every import path at the boundary; filter every query by `user_id`; keep the original file untouched; write via `.part` then rename; run all suites, both builds and the lint before calling a task done; update `doc/` where the code diverges.
- **Ask first:** any dependency beyond those listed above; schema changes beyond this data model; changing the 50 GiB limit or the format list; adding a WebSocket gateway or touching the Python service.
- **Never:** run FFmpeg/FFprobe from NestJS; follow symlinks or copy from inside `MEDIA_ROOT`; log full file paths of user media at info level with secrets (paths are fine, contents never); load a whole video into memory; edit generated migrations by hand once committed.

## Success Criteria

1. A project can be created, listed, renamed and deleted from the desktop. An empty or 101-character name is rejected inline and by the API (400).
2. Importing an mp4 through the native dialog shows the row at once as IMPORTING with a progress %, then READY. The copy at `MEDIA_ROOT/original-videos/{user}/{project}/{video}/source.mp4` has the same sha256 as the original, and the original's mtime is unchanged.
3. Each of these returns 400 with a clear message and writes nothing: a directory, a symlink, a `.txt`, a `.txt` renamed to `.mp4`, an empty file, a file over the size limit, insufficient free space, a path inside `MEDIA_ROOT`, a non-existent path.
4. After restarting the API and the desktop, every project and READY video is still listed.
5. If the API is killed mid-import and restarted, the video shows FAILED ("Import interrupted…") and no `.part` file or directory remains.
6. Deleting a video (including one still importing) or a project removes its rows and its media directory.
7. An unknown or foreign id gives 404, and a malformed id gives 400.
8. All test suites, both builds, the API lint and `cargo check` pass. The code review finds no open Critical or Required findings.
9. `doc/` is updated: the auth decision (architecture §11, system-design §15), the video statuses `IMPORTING/READY/FAILED` (system-design §4.1, replacing `UPLOADED`), the table fields (architecture §9.1), and the Phase 2 task list.

## Out of Scope (Deferred)

- Login, accounts and multiple users: not needed on a single local machine. The `CurrentUser` seam keeps the option open.
- Duration, resolution and fps (FFprobe): Phase 3, in the Python service.
- `GET /videos/:id/file` streaming and video preview: Phase 7, the clip and preview experience.
- WebSocket progress: Phase 3, with job progress.
- Drag-and-drop import: native dialog first. Add it if users ask.
- Limiting concurrent copies and resumable imports: single user, rare. Re-import is the recovery path.
- Duplicate-file detection, project search, sorting and pagination: lists are small for one local user.
- Thumbnails for source videos: Phase 6 renders thumbnails.

## Resolved Questions

1. **Test database:** use a dedicated `clipforge_test` database (owner `vanex`, port 5433), read from `TEST_DATABASE_URL`. It's created once with `sudo -u postgres createdb -p 5433 -O vanex clipforge_test`.
2. **Size limit:** 50 GiB per file, confirmed.
3. **Formats:** all common video formats (validation rules 3–4). Files that are a video container but undecodable are caught by FFprobe in Phase 3.
